# 영등포구 북부(여의도) SUMO 도로 환경 — 공식 도로망 + 실측 교통량

- **도로**: 국토교통부 국가표준노드링크 (차로 수·제한속도·지하차도/고가·회전 제한 포함)
- **교통량**: 서울시 TOPIS 교통량 조사 (평일 시간대별 실측, 측정 지점 10곳)
- **배경**: OSM 건물·공원·한강, 신호 위치

같은 도로에서 **심야 / 주간 / 출근** 세 가지 교통량을 만든다.

## 범위

경도 126.880~126.950, 위도 37.505~ **한강 중앙선** (다리는 강 중간에서 자름).
영등포구 북부(여의도·당산·양평·영등포·문래·신길 북부)와 맞닿은 노량진·대방, 신도림 일부.

## 설치 (한 번만)

새 환경 설치와 SUMO_HOME 설정은 [루트 README](../README.md#설치)를 따른다.
이미 준비된 환경에서 도로 구축 도구만 추가하려면:

```bash
source .venv/bin/activate
python -m pip install -r yeouido/requirements.txt
```

표준노드링크 원본은 용량이 커서(약 270 MB) 직접 받는다:
국가교통정보센터(its.go.kr) → 교통데이터 → 표준노드링크 → 최신 zip을
`env/yeouido/source/nodelink/raw/` 에 압축 해제 (`MOCT_LINK.*`, `MOCT_NODE.*`, `TURNINFO.dbf`).
현재 사용본: 2026-10-14.
원본이 없으면 `run_all` 은 추출 단계를 건너뛰고 git 에 있는 `source/nodelink/region.json` 을 그대로 쓴다
(범위를 바꾸거나 새 노드링크를 쓸 때만 원본이 필요).

## 실행

```bash
python -m yeouido.run_all --skip-validate  # 전체 환경 생성 (다운로드·실행 환경에 따라 소요 시간 변동)
python -m yeouido.validate                 # 70분 시뮬레이션 검증 (수준별 수 분)
python -m yeouido.live                     # sumo-gui + 시간대 전환 버튼 (심야/주간/출근)
python -m yeouido.view --level rush        # sumo-gui, 한 시간대 고정 (night / day / rush)
```

`live` 는 sumo-gui 옆에 조절 창을 띄운다. 버튼을 누르면 그때부터 새로 들어오는 차량이 그 시간대
일정표를 따르고, 이미 달리는 차는 그대로 빠져나간다 (출근 → 심야로 바꾸면 정체가 서서히 풀린다).
재생 속도는 sumo-gui 상단 Delay(ms) 로 조절한다.
출발·도착을 선택해 차량을 직접 주행하려면 [경로 도구](../yeouido_cross/README.md)를 사용한다.

일반 차량과 ego 모두 승용차 차체·창문이 보이도록 GUI의 차량 표시 품질을 지정한다.
`view`·`live`와 경로 주행 도구에 함께 적용되며, 설정 변경 뒤에는 창을 재실행한다.

### 지하차도 색상 표시

`yeouido.view`와 `yeouido.live`는 지하차도(표준노드링크 도로 유형 `002`)를 밝은 회색,
일반 도로를 짙은 회색으로 표시한다. SUMO 1.27.1에서 확인했다.
실행할 때 `yeouido.visualization`이 원본에서 색상용 파라미터만 추가한
`env/yeouido/yeouido.underpass.net.xml`과 `underpass_visualization.json`을 재생성한다.
원본 도로망의 차로 연결·신호·형상과 교통 수요는 이 표시 기능으로 변경되지 않는다.
큰 교차로 도형이 지하차도를 가리면 `Ctrl+J`로 도형을 숨겨 내부 차로를 확인할 수 있다.

현재 `final`의 `DEMAND_SCALE = 1.0`과 세 시간대 차량 파일을 그대로 사용한다.
추가로 `--scale 4`를 주면 실측 100%를 넘어 중복 증폭되므로 사용하지 않는다.

### T DATA 실측 신호

**현재 자료만으로 모든 교차로가 실제 신호와 동일하다고 검증할 수 없다.** 아래 30곳도 부분 관측에서
추출한 반복 주기이며, 차로 대응과 우회전·유턴 처리에 모델링 가정이 있어 전체 운영계획의 복제본이 아니다.
현재 입력에는 모든 교차로의 검증된 현시도·시간대별 운영계획(TOD) 원본이 없다.

전체 228개 제어기의 위치, 진입 도로, 공식 MAP 대응 후보, 현재 신호 출처와 누락 근거를 확인하려면:

```bash
python -m yeouido.audit_signals
python -m yeouido.audit_signals --require-verified
```

결과는 `env/yeouido/signal_audit/inventory.csv`와 `inventory.json`이다.
`--require-verified`는 현장 동일성 검증이 완료되지 않으면 종료 코드 2를 반환한다.
비보호 좌회전 목록은 점검 대상이며, 비보호 좌회전 자체가 오류라는 뜻은 아니다.
위치 후보가 없다는 결과도 해당 도로에 실제 신호가 없다는 뜻은 아니다.

실제 신호 전수 재현에는 서울 지역의 제어기·차로 대응, 현시 순서와 보호/비보호 규칙,
황색·비움 시간, 시간대별 운영계획·주기·옵셋, 자료 기준일과 현장 대조가 필요하다.
[T DATA 실시간 API](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=10381)는
호출 시점의 상태·잔여시간 서비스다. 운영계획 API의 서울 제공 여부는
[공공데이터포털 설명](https://www.data.go.kr/data/15056569/openapi.do)과
[UTIC 현행 안내](https://www.utic.go.kr/guide/utisRefSig.do)의 지역 범위가 달라 별도 확인이 필요하다.

사용자가 제공한 **2026-11-16 신호제어기 신호 정보 CSV**를 현재 도로망에 연결했다.
전체 신호 제어기 228개 중 **51개**에 관측 주기를 적용한다.
심야 03시는 4개, 주간 12시는 51개, 출근 08시는 44개이며, 시간대별 적용 대상이 다르다.
나머지는 기존 SUMO 감응식 신호와 사용자 지정 여의2교 남단 순서를 유지한다.
기존 11월 13일 자료 대신 이 파일을 기본 재생성 자료로 사용한다.
실시간 신호를 계속 따라가는 방식이 아니라, 같은 시간대에서 두 번 이상 확인된 완전한 주기를 반복한다.

- 교차로 중심 거리 50m 이내, 진입 방향과 차로 연결이 맞는 경우만 사용한다.
  [노드 MAP](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=10147)과
  [신호연결 MAP](https://t-data.seoul.go.kr/dataprovide/trafficdataviewfile.do?data_id=10146)의 진입 방향도 비교한다.
- 관측 공백을 신호 유지 시간으로 채우지 않는다. 녹색 종료 시 황색이 관측되고 모든 이동류에 녹색이 있는
  반복 주기만 사용하며, SUMO 도로 형상에서 보호 녹색이 상충 녹색·황색과 겹치는 경우는 제외한다.
  일부 방향의 직진이 유지되는 동안 다른 방향이 비워지는 실측 주기도 허용한다.
  결측 상태는 구간을 끊는 경계로 처리하고, 그 밖의 정상 구간에서 두 번 이상 확인한 주기를 사용한다.
- 우회전은 같은 진입로의 직진 신호를 따르며 녹색에도 양보한다. 별도 유턴 신호가 없으면
  관측된 좌회전 신호에서만 양보하며 유턴한다. 따라서 현장 우회전·유턴 규칙까지 완전히 재현하지는 않는다.
- `signals_{night,day,rush}.add.xml`을 `view`, `live`, 학습 환경, `validate`에서 함께 읽는다.
  `live` 버튼으로 시간대를 바꾸면 현재 전체 적색이 끝난 뒤 제어기별로 전환한다.
  전체 적색이 없는 주기는 전환할 때만 황색(최소 3초)과 전체 적색 8초를 거친다.
  이는 프로그램 교체를 위한 비움 단계이며 평소 실측 주기에는 추가하지 않는다.
  신호 파일이 변경되면 학습용 워밍업 상태도 다음 실행 때 재생성한다.
- 적용 교차로·주기와 제외 이유: `env/yeouido/signals_tdata_report.json`.
  교통량 배율은 기존 `1.0`을 유지한다. 전체 도로망의 정체·충돌 해결을 보장하는 변경은 아니다.

기존 `view`/`live` 실행 명령을 그대로 쓰면 적용된다. 열린 창은 종료 후 다시 실행한다.
도로망을 수동으로 재생성했다면 다음 명령으로 신호를 다시 매칭한다 (`run_all`은 자동 수행).
차량 수요만 재생성할 때도 신호 파일 연결을 유지한다.

```bash
python -m yeouido.tdata_signals
```

재생성에 필요한 축약 관측과 MAP 진입 방향은 `env/yeouido/source/signals/`에 있다.
서울 전체 대용량 원본 CSV·ZIP은 저장소에 포함하지 않는다. 최신 원본으로 바꾸려면 공식 포털에서
신호 및 잔여시간 ZIP, 교차로 MAP CSV, 노드 MAP CSV, 신호연결 MAP CSV를 받은 뒤 실행한다.

```bash
python -m yeouido.tdata_signals --history /path/signals.zip \
  --crossroads /path/crossroads.csv --nodes /path/nodes.csv --connections /path/connections.csv
```

발급받은 **(실시간) 신호제어기 신호정보 현시 서비스**의 인증 확인은 아래처럼 한다.
키는 환경변수 `TDATA_API_KEY` 또는 Git에서 제외되는 로컬 `.env`에만 둔다.
`--probe`는 신규 `v2xSignalPhaseCurrentInfo/1.0`만 호출하며 구 API로 우회하지 않는다.
현재 시점 상태 한 건만으로 전체 신호 시간표를 만들 수는 없다.

```bash
python -m yeouido.tdata_signals --probe 148
```

### 신규 실시간 API 수집 결과 (2026-11-17)

사용자 제공 이력 파일을 추가 분석한 결과는 아래 [11월 16일 CSV 분석](#사용자-제공-11월-16일-csv-분석)에 있다.
이력 파일에 필요한 시간대가 포함되어 있다면 그 날짜의 재구성을 위해 실시간 API를 다시 수집할 필요는 없다.

신규 서비스에 기존 키로 접근했고, 영등포·동작·강서·구로·양천의 5개 시군구를 조회했다.
현재 공식 MAP 목록의 범위 내 교차로 190곳 중 147곳이 응답했다.
약 206초 동안 197개 지역 조회 묶음을 기록했으며, 141곳에서 신선한 상태를 관측했다.
수집 도중 서버가 HTTP 429와 호출 한도 1,000회를 반환해 중단했다.
한도 적용 기간은 이 응답만으로 단정하지 않으며 `X-RateLimit-Reset` 원문을 결과에 보존했다.

수집 기록은 **2026-11-17 22시**의 상태이며, 심야 03시·출근 08시·주간 12시 계획으로 재사용하지 않았다.
현재 주기 후보·제어기 연결의 누락·수집 한도는 `signal_audit/current_service.json`에 기록한다.
이는 전체 실제 신호 적용 완료 보고서가 아니며 현재 실행 신호 파일을 변경하지 않는다.

```bash
# 한 번 조회하여 키·수신 범위 확인
python -m yeouido.tdata_current

# 이후 한도가 허용할 때만 실행: 5개 구, 8분, 3초 간격 (예상 약 805회)
python -m yeouido.tdata_current --seconds 480 --interval 3

# 영등포만 좁혀 기록 (다른 구의 신호는 수집하지 않음)
python -m yeouido.tdata_current --districts 11190 --seconds 480 --interval 1

# 실제 출력된 기록 파일 경로를 지정하여 주기 후보·누락 분석
python -m yeouido.tdata_current --analyze /path/current_recording.jsonl.gz
```

실행당 요청 예산은 기본 900회이며 예상 요청 수가 이를 넘으면 네트워크 호출 전에 거부한다.
서버가 429를 반환하면 자동 재시도하지 않는다. 수집 간격을 늘리면 짧은 황색 등 상태 변화를 놓칠 수 있어
주기 후보가 나오지 않을 수 있다. 오래되거나 시각이 없는 응답은 신선한 상태로 세지 않는다.
원본 기록은 Git에서 제외되는 `source/signals/live/`에 보관한다.

### 사용자 제공 11월 16일 CSV 분석

`signalPhase_20261116/signalPhase.csv`(약 21.3GB)를 전체 스캔했다.
76,493,009행, 전체 2,529개 교차로의 기록이며, 프로젝트 MAP 범위의 190곳 중 142곳이 포함됐다.
0~23시 모든 시간대의 기록이 있지만, 개별 교차로의 기록은 중간에 끊길 수 있다.

| 시간대 | 기록이 있는 교차로 | 적용한 SUMO 제어기 |
|---|---:|---:|
| 심야 03시 | 141 | 4 |
| 주간 12시 | 142 | 51 |
| 출근 08시 | 141 | 44 |

중복 제외 51개 제어기에 실제 적용했다. 현장 동일성 검증 완료를 뜻하지는 않는다.
초기 시험의 36개에서, 불필요한 전체 적색 조건을 없애고 정상 관측 구간을 활용하면서 확대했다.
대신 보호 녹색과 상충 황색의 중첩 검사를 추가해 일부 심야 후보는 제외했다.
이 파일은 신호 상태 이력이므로, 실제 제어기와 SUMO 차로 연결에 필요한 MAP 대응을 대신하지 않는다.

추출 관측은 `source/signals/observed_cycles_20261116.json`, 상세 분석은
`signal_audit/history_20261116.json`에 있다. 적용 내역과 제외 사유는
`signals_tdata_report.json`, 전체 228개 제어기의 시간대별 출처는 `signal_audit/inventory.csv`에서 확인한다.
아래 명령은 관측 추출만 수행하며, 신호 파일을 생성하거나 실행 설정을 바꾸지 않는다.

```bash
python -m yeouido.tdata_signals \
  --history ~/Downloads/signalPhase_20261116/signalPhase.csv \
  --crossroads env/yeouido/source/signals/crossroads.json \
  --records-out env/yeouido/source/signals/observed_cycles_20261116.json
```

CSV와 ZIP을 모두 지원한다. 대용량 원본은 스트리밍으로 읽고, 대상 교차로·시간대만 추출한다.
패킷 시각이 뒤섞인 경우 정렬한 뒤 주기를 구성하며, 같은 시각에 모순된 신호가 있으면 미확인 상태로 남긴다.
이미 추출한 11월 16일 자료로 실행 신호를 다시 만들려면 `python -m yeouido.tdata_signals`를 실행한다.

## 도로망 만드는 방법 (`build_net.py`)

1. 범위 경계를 넘는 링크는 경계점까지만 남긴다.
2. 도시고속도로(올림픽대로·서부간선도로)는 뺀다. 측정값이 없고, 내려오는 램프가 범위 입구가 된다.
3. **교차로 합치기**: 표준노드링크는 한 교차로를 진입·진출 지점별 노드 여러 개로 나누고 짧은
   링크로 잇는다 (분리대가 있는 도로끼리 만나면 네모 모양 노드 4개). 교차로 노드 두 개가 링크로
   직접 이어져 있고, 그 링크가 20 m 이하이거나 이름(표기 차이 정리 후)이 같고 30 m 이하이면 합친다.
   - 주소로 이름이 제각각인 귀퉁이 노드(선유로×문래북로)도 구조로 합쳐진다.
   - 이름만 같고 연결되지 않은 노드(신도림고가차도 옆 분기점)나 35 m 떨어진 별도 합류점(마포대교앞)은 합치지 않는다.
   - **높이가 다른 노드(고가 위·지하·지상)는 합치지 않는다** → 지하차도·고가가 평면 교차로가 되지 않는다.
4. 1차로 골목길("○○로8길" 등)은 뺀다. 단, 교차로 내부를 잇는 링크는 남긴다 (영등포로터리의 한 변이 "영등포로53길").
5. 차로 수·제한속도·도로명은 링크 값 그대로, 회전 제한(좌·직·우회전 금지)은 실제 자료대로.
6. 신호: OSM 신호 표시 근처, 또는 간선도로 교차로. 기본은 감응식, **양방향 직진 동시 + 보호 좌회전 단계**
   (한국 간선도로 방식). 방향별 순차 신호보다 출근 시간 정체 teleport가 적고 평균 속도가 높았다.
7. **전체 적색 시간을 교차로 크기에 맞춤** (2~8초): 여의대로처럼 넓은 교차로는 2초 안에 다 건너지
   못한 차가 교차로 안에 갇혔다 (마포대교 남단).
8. 신호 없는 합류는 비슷한 두 도로가 만나 차로가 줄 때만 지퍼식 교대 합류, 보조 차로가 붙는 곳은 본선 우선.
9. **검수 수정 목록** (`yeouido/corrections.json`, `corrections.py`): 항공사진 검수로 확인한 차이만 원본 위에
   덧붙인다. 지원하는 수정은 여섯 가지다 (새 도로 `add_links` 포함) (형식은 `corrections.py` 설명).
   - 회전 제한 지우기 (`remove_turns`): 노드링크 TURNINFO 중 실제와 다른 금지(from → to)를 빼고 만든다.
   - 도로 삭제 (`remove_links`): 실제로 없는 도로(한 방향 링크)를 뺀다. 교차로 합치기 뒤에 빼고, 그 때문에 끊긴
     조각도 같이 빠진다. `region.json` 은 그대로라 원본을 다시 뽑아도 삭제가 유지된다.
   - 차로 수 (`lane_counts`): 도로 전체 차로 수를 노드링크 값 대신 쓴다. 중앙선 쪽 가장자리는 그대로 두고
     바깥쪽으로만 넓히거나 좁힌다 (도로선을 바뀐 폭의 절반만큼 오른쪽으로 옮김). 우선순위는 원래 차로 수 기준 그대로.
   - 좌회전·우회전 포켓 (`turn_pockets`): 교차로 직전에 늘어나는 회전 전용 차로. 포켓 구간도 바깥쪽으로만 넓힌다. 노드링크는 링크마다
     차로 수가 하나라 이런 차로가 빠지고, 맨 왼쪽(오른쪽) 차로가 직진·회전 공용이 된다. 이 경우 `opposites`
     신호는 보호 좌회전 단계를 만들지 않는다 (좌회전 전용 차로가 있어야 만든다).
     포켓 도로의 차로별 연결은 직접 정하고(새 차로 = 그 회전 전용, 원래 차로에서 그 회전을 뺌), 포켓 길이는
     정지선부터 잰 길이가 되도록 만든 뒤 재서 맞춘다.
   - 차로별 방향 (`lane_moves`): 정지선 차로 하나의 직진·좌회전·우회전. netconvert 가 추정한 연결 대신
     그 진입로의 차로별 연결을 전부 직접 적는다. 도로 단위로 갈 수 있는 곳은 바뀌지 않는다.
   검수 도구 카드의 버튼·단축키로 고친다 (`inspection/README.md`).
   수정 전후 비교: `python -m inspection.compare_nets --sim rush` (`inspection/README.md`).

이전 OSM 기반 방식은 `build_net_osm.py` 에 참고용으로 남겨 두었다 (비교: `env/yeouido/compare_yeouigyo.png`).

가장 가까운 차도(지하차도·고가 제외)에 연결했다.

**외곽 게이트 A~F** (`count_edges.json`): A 서강대교, B 마포대교, C 원효대교,
D 양화대교, E 오목교, F 경인로(거리공원).
샛강 연결로는 **ㄱ 여의교 · ㄴ 서울교 · ㄷ 여의2교**로 구분한다.
경로 주행 도구는 랜드마크 7곳과 외곽 게이트 6곳, 총 13개 핀포인트를 사용한다.

## 학습 환경 (`env/yeouido_env.py`)

`env/road_config.py` 의 `ROAD_TYPE = "yeouido"` 이면 `train.py` / `test.py` / `collect_pomdp_data.py` 가
이 도로를 쓴다. 설정은 같은 파일의 `YEOUIDO_ROAD`.

- 리셋: 시간대(심야/주간/출근)를 뽑고, 배경 교통이 흐르는 워밍업 상태(600·1200·1800·2400초)를 불러온다.
  상태 파일은 처음 한 번 `env/yeouido/states/` 에 만들어진다 (도로망·교통량을 다시 만들면 자동 갱신).
- ego: `places` 설정에 따른 랜드마크·게이트에서 출발지와 목적지(경로 1 km 이상)를 고른다.
  현재는 `landmarks+gates`이며, 목적지 지점 도착을 완주로 처리한다.
  `env.reset(options={"level": "rush", "origin": "영등포역", "destination": "IFC 서울"})` 로 고정 가능.
- 주행 중 목적지 변경: `env.change_destination("63빌딩")` (경로 재탐색), 남은 거리는 `info["remaining"]`.
- 행동은 수업 환경과 같다. 보조 장치: 빨간불 정지(`signal_assist`), 제한속도(`obey_speed_limit`),
  경로상 필요한 차로 변경은 SUMO가(`lane_change_mode=1`). 교차로 안 충돌도 검사(`check_junction_collisions`).
- 관측 40차원 = 수업 환경 31 + 신호 색·정지선 거리·다음 교차로 거리·경로 차로 오프셋·차로 지속 거리·
  남은 경로 비율·제한속도·교차로 상대 차량 거리·양보 관계 (`env/mdp_config.py` OBSERVATION).
- 보상: 진행 거리(1 m당 0.002) − 시간(스텝당 0.002) − 빨간불 통과(2) − 충돌(5) + 도착(2).
  정체·신호 대기 중에는 차간거리·막힘 벌점을 주지 않는다. 할인율 0.995 (`train.py`).
- 차로 변경 입구 보호(시작 60 m 변경 금지)는 배경 차량이 생기는 경계 도로에서만.
- 점검 (IDM 규칙 정책, 9회): 신호 보조 켬 → 9회 도착, 빨간불 0, 평균 return +7.5.
  신호 보조 끔(빨간불 무시) → 빨간불 36회, 충돌 1, 평균 return −1.0 (보상이 신호 위반을 구분함).
- 선생님 데이터: `python collect_pomdp_data.py --policy sumo-expert --episodes 500 --workers 4`
  (`algorithms/sumo_expert.py`, SUMO 운전자 모델의 차량추종·신호·양보·차로변경 판단을 행동으로 기록).
  100회 수집 시 선생님 96회 도착 / 충돌 4, 평균 31 km/h.

| 정책 (12회 평가) | 충돌률 | 완주율 | 평균 속도 |
|---|---|---|---|
| BC ← 무작위 데이터 100회 | 50% (2회 평가) | 50% | 6 km/h |
| BC ← 선생님 데이터 100회 | 25% | 75% | 36 km/h |

## 이전 검증 결과 (70분, 실측 × 0.25, T DATA 신호 적용 전)

충돌 판정은 수업 환경(`env/sumo_env.py`)과 같은 SUMO 기본값(차로 위 충돌).

| 수준 | 투입 차량 | 측정 지점 GEH<5 | teleport | 일반 차량 충돌 | 평균 속도 | 평균 대기 |
|---|---|---|---|---|---|---|
| 심야 | 1,208 | 20/20 | 0 | 0 | 38.3 km/h | 43 s |
| 주간 | 7,144 | 20/20 | 0 | 0 | 36.7 km/h | 49 s |
| 출근 | 9,247 | 20/20 | 2 (양보 대기) | 0 | 35.0 km/h | 71 s |

- 출근 수준은 주간보다 차가 약 30% 많고, 평균 대기가 1.5배로 길다.
- `--strict`(교차로 안 충돌까지 검사)로 보면 출근 수준에서 11건이 잡힌다. 넓은 교차로 안에서
  휘어진 경로들이 서로 너무 가깝게 겹치는 모양 문제이며, 수업 환경 기준에는 포함되지 않는다.

도로 데이터별 비교 (출근, 실측 × 0.4, 40분, 교차로 안 충돌까지 검사):

## 한계

- 현재 `DEMAND_SCALE = 1.0`. 이전 추정 신호 실험에서는 0.4 이상에서 주간·출근 정체가 계속
  쌓였다. T DATA 신호를 적용하지 못한 교차로는 SUMO 추정 신호이므로 실제 처리량과 차이가 있다.
  세 수준 모두 같은 배율이라 **시간대 간 비율은 실측 그대로**다.
- 섬 안쪽 도로 교통량과 교차로 회전 비율은 실측이 없어 routeSampler가 추정한다.
- 출발·도착을 범위 경계에만 두어, 여의도 업무지구에 주차하는 차는 표현하지 않는다.
- 도시고속도로(올림픽대로·서부간선도로)는 측정값이 없어 넣지 않았다.
